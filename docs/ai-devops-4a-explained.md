# AI DevOps 4A 架构（小白版）

这份说明不用任何技术背景也能读懂。你只要记住一个比喻：AI DevOps 是一座"智能交付工厂"。

## 一句话理解 4A

4A 是四个视角，不是四套系统：

| 视角 | 问题 | 工厂比喻 |
| --- | --- | --- |
| BA 业务架构 | 工厂生产什么、流程是什么？ | 接单 → 备料 → 加工 → 质检 → 发货 |
| AA 应用架构 | 工厂里有哪些车间和岗位？ | 接单台、仓库、质检线、发货口 |
| TA 技术架构 | 用什么机器、水电、厂房？ | 服务器、数据库、Docker、镜像仓库 |
| IA 信息架构 | 账本和图纸怎么记？ | 订单、物料、成品编号，每样只记一份 |

## BA 业务架构：平台为你做什么

业务链路只有五步：

1. 交付接入：Codex、WorkBuddy 等研发工具把代码和版本交给平台；
2. 版本管理：每次发布都固定到一个 commit，不 deploy "最新代码"；
3. 质量门禁：自动构建、测试、安全扫描；
4. 多环境发布：开发/预发自动执行，生产必须你点"批准"；
5. 上线运维：容器部署、健康检查、失败自动回滚。

你的角色只有三个动作：提需求（给智能体）、看结果（浏览器）、批生产（点一次按钮）。

## AA 应用架构：平台由哪些"车间"组成

- 接入层：Web 控制台、Agent Bridge（MCP / 令牌 API）；
- 统一网关：认证、限流、审计，所有入口共用；
- 应用服务：身份权限、仓库版本、应用模板、流水线、部署审批、多云适配、数据库管理、终端环境；
- 横切服务：凭据、审计、故障诊断，只建一套，全模块复用；
- 执行与外部：Runner 构建、TCR 镜像、容器部署、Gitee、云厂商、MySQL/服务器。

判断标准：一个能力只有一个服务，不允许每个模块各做一套登录、权限、日志。

## TA 技术架构：用什么技术，部署在哪

- 客户端：浏览器 + 智能体/IDE；
- 本机控制面（D 盘）：React 控制台 + Node/Fastify API + SQLite 元数据 + 加密凭据库；
- 云服务器（203.0.113.10，文档示例地址）：Docker + Compose 运行业务容器，MySQL 提供数据库；
- 外部服务：Gitee 代码、腾讯云 TCR 镜像仓库、腾讯云 API。

为什么这样选：本地维护方便、服务器只跑容器容易迁移、凭据与业务代码分离更安全。

## IA 信息架构：数据为什么不会重复

四组核心数据：

- 身份与权限：用户、角色、字段级权限、智能体令牌；
- 交付与版本：仓库、版本 commit、应用、流水线、运行、部署；
- 多云与运维：云账号、云资源、服务器、数据库、备份、凭据；
- 审计与证据：审计事件、错误诊断、健康检查结果。

一条主线：仓库 → 版本 → 流水线 → 运行 → 部署 → 服务器。

重要规则：总览、运行历史、部署面板都是"实时汇总视图"，不复制任何数据。所以总览的 16 个云资源就是资源模块里的 16 个，4 次部署就是部署记录里的 4 次，永远对得上。

## 防冗余六条铁律

1. 一份事实只存一处：commit、部署、云资源、审计各自只有一张表；
2. 安全能力只建一套：认证、权限、凭据、审计、诊断全平台共用；
3. 所有入口走统一网关；
4. 所有发布走同一条 Runner 和审批链；
5. 汇总视图不存数据副本；
6. 新项目复用平台能力，缺什么补平台，不按项目复制一套。

## 名词小抄

- commit：代码的一个固定版本号，像快递单号；
- CI/CD：自动构建、自动测试、自动发布；
- Runner：真正执行构建和部署的"机器人工作台"；
- TCR：腾讯云镜像仓库，存放打包好的应用镜像；
- 容器：把应用和运行环境一起打包，换服务器也能直接运行。
